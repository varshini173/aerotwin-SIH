# AeroTwin — AI-Enabled Digital Twin for MALE UAV Engine Health Monitoring

**Smart India Hackathon 2026 — Theme: Robotics and Drones — Category: Software**

**Project Title:** AI-Enabled Digital Twin for Predictive Health Monitoring, RUL
Estimation and Mission Reliability Assessment of MALE UAV Engines

A complete, runnable-locally software prototype: an engine telemetry simulator,
a preprocessing + feature-engineering pipeline, three real ML models (anomaly
detection, fault classification, RUL regression), a rule-based digital-twin
and mission-risk layer, a FastAPI + WebSocket backend, and a React/Vite
dashboard (built on the provided Stitch UI design) with five pages: Overview,
Digital Twin, Live Monitoring, Mission Readiness, and History/Replay.

> **This is a student prototype and decision-support system.** It does **not**
> claim exact crash prediction, guaranteed failure prediction, certified
> aviation safety, or exact real-world engine lifetime. All ML models are
> trained on **synthetic data generated by the included simulator**, not a
> real UAV engine. See [Limitations](#limitations) below.

---

## Quick Start

**Requirements:** Python 3.10+ and Node.js 18+ installed and on PATH.

1. Extract this zip anywhere and open the extracted folder in VS Code
   (File → Open Folder... → select the folder that directly contains
   `backend`, `frontend`, `docs`).
2. Run the setup script **once**:
   - Windows: double-click `setup.bat` (or run it from a terminal)
   - macOS/Linux: `chmod +x setup.sh && ./setup.sh`
3. Start the app any time after that:
   - Windows: double-click `start.bat` — opens two windows and your browser
   - macOS/Linux: `./start.sh` — Ctrl+C stops both servers
   - **Or, inside VS Code:** press `Ctrl+Shift+B` (Cmd+Shift+B on Mac), or
     `Terminal → Run Task... → AeroTwin: Start Full Stack`. This starts both
     the backend and frontend in two VS Code terminal panels — no separate
     windows, no manual `cd`.
4. Open `http://localhost:5173/` if it doesn't open automatically.

If you'd rather run each side manually (e.g. to see backend logs
separately), see [Installation & Running Locally](#4-installation--running-locally)
below or `docs/setup.md`.

## 1. Architecture

```
Engine Simulator / Arduino UNO + 5 Potentiometers (backend/hardware/)
        |
Data Acquisition  (simulator.tick())
        |
Data Preprocessing  (validation, outlier clip, moving avg, rate of change)
        |
Feature Engineering  (14-dim feature vector)
        |
   AI / ML Processing
   |        |         |
Anomaly   Fault     Degradation
Detection Prediction  Estimation
   |________|_________|
        |
RUL / Time-to-Critical (Gradient Boosting regression)
        |
Digital Twin (state + alerts)
        |
Mission Assessment (risk / readiness / recommendation)
        |
FastAPI  ->  REST + WebSocket (/ws/engine)
        |
React (Vite) Frontend  ->  SIH Dashboard (5 pages)
```

The simulator is fully decoupled from everything downstream: it only needs to
produce a dict of `{rpm, temperature, vibration, pressure, load}` per tick.
The `backend/hardware/` folder does exactly this: an Arduino UNO with 5
potentiometers plus `backend/hardware/serial_bridge/bridge.py` feeds real sensor
data into the same `{rpm, temperature, vibration, pressure, load}` schema
via `backend/simulator/hardware_ingest.py` — no other backend module
changes. See `backend/hardware/README.md` for wiring and run steps.

## 4. Installation & Running Locally

### Backend

```bash
cd backend
python -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # macOS/Linux
pip install -r requirements.txt
uvicorn main:app --reload
```

Backend runs at `http://127.0.0.1:8000`. Interactive API docs at
`http://127.0.0.1:8000/docs`. The saved ML models in `backend/saved_models/`
are already trained and committed — the backend loads them at startup. To
retrain from scratch (optional):

```bash
cd ..
python ml/training/train_models.py
```

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Frontend runs at `http://localhost:5173` and connects to the backend via
REST (`http://127.0.0.1:8000`) and WebSocket (`ws://127.0.0.1:8000/ws/engine`).
Both must be running simultaneously.

No GitHub required. No cloud deployment required. No real UAV engine required.

## 5. ML Explanation

All three models are trained in `ml/training/train_models.py` on data
generated by driving the **same** simulator/preprocessing/feature pipeline
used at inference time through all 7 scenarios (Normal, Overheat, Vibration,
RPM Instability, Pressure Abnormality, Combined Degradation, Progressive
Degradation), so the models see the exact feature distributions they'll be
asked to score live.

- **Anomaly Detection — Isolation Forest**, fit on healthy-only samples.
  Outputs a 0–100 anomaly score and a normal/abnormal flag.
- **Fault Classification — Random Forest**, supervised, 7 classes (6 fault
  types + NONE). Outputs predicted fault type and a 0–100% fault risk
  (`1 - P(NONE)`).
- **RUL / Time-to-Critical — Gradient Boosting Regression**, supervised,
  trained against a ground-truth "hours until severity reaches the critical
  threshold" computed analytically from each scenario's known degradation
  ramp rate during data generation. Outputs estimated RUL (hours) and
  estimated time to critical condition (minutes).

See `ml/evaluation/metrics.md` for accuracy/precision/recall/F1 (classification)
and MAE/RMSE/R² (regression), computed on a held-out synthetic test split.

**Engine Health** and **Degradation** scores are derived (not directly
modeled) — see `backend/prediction/predictor.py` for the exact blend formula
of the combined-degradation feature, anomaly score, and fault risk.

## 6. RUL Explanation

RUL ground truth during training is generated at a resolution of **1
simulated tick = 1 simulated minute** of engine operating time, independent
of the **live demo's 1-tick/second playback speed** (which is deliberately
compressed for demonstration purposes — watching a real multi-hour
degradation in real time isn't practical in a hackathon demo). This means:
live RUL/time-to-critical numbers are estimates of engine-operating-time
remaining, not wall-clock demo time remaining. This tradeoff and its
implications are documented here explicitly rather than hidden.

## 7. Mission Risk Explanation

Given a planned mission duration and expected load, `backend/mission/mission_assessment.py`
computes an effective required-RUL (mission duration scaled up for
higher-than-baseline load) and compares it against the current estimated RUL
with a 1.5x safety margin for LOW risk, 1.1x for MODERATE, else HIGH. Health
and fault-risk floors can independently force a HIGH-risk verdict even if
RUL alone looks sufficient.

## 8. API Endpoints

| Method | Path | Description |
|---|---|---|
| GET | `/` | API info |
| GET | `/api/engine/status` | Full current digital twin state |
| GET | `/api/engine/prediction` | Health/degradation/fault/RUL only |
| GET | `/api/engine/mission-risk` | Current mission risk/readiness |
| GET | `/api/engine/history?run_id=&limit=` | Recent samples for a run |
| GET | `/api/engine/runs` | List of all runs |
| GET | `/api/engine/runs/{run_id}` | Full sample history for one run (replay) |
| POST | `/api/engine/start` | Resume ticking |
| POST | `/api/engine/reset` | Reset engine to healthy baseline, start new run |
| POST | `/api/engine/scenario` | Body: `{"scenario": "OVERHEAT"}` |
| POST | `/api/engine/mission` | Body: `{"duration_hours": 2, "expected_load_percent": 60}` |
| WS | `/ws/engine` | Live state broadcast, ~1 Hz |

## 9. Fault Simulation

The Overview page's Simulation Controls panel calls `POST /api/engine/scenario`,
which changes the backend simulator's target scenario. Severity ramps up
gradually (not instantly) tick by tick, so the full pipeline — sensors →
preprocessing → features → ML → health/degradation/RUL → mission risk →
dashboard — visibly evolves over the following ~30–60 seconds, exactly as
required for a convincing demo. See `docs/demo.md` for the exact sequence.

## 10. Limitations

- By default, all telemetry is **simulated**. In hardware mode
  (`USE_HARDWARE=1`, see `backend/hardware/README.md`) it comes from a real
  Arduino UNO + potentiometer rig, not a real UAV engine.
- All ML training data is **synthetic**, generated by the same simulator —
  results in `ml/evaluation/metrics.md` measure how well the models learn the
  simulator's fault signatures, not real-world engine reliability.
- RUL/time-to-critical are prototype estimates on a simplified simulated
  timescale (see RUL Explanation above), not certified predictions.
- Single-engine, single-session state (in-memory + one SQLite file) — not
  designed for multi-tenant/production deployment.
- No authentication on the API — local development use only.

## 11. Future Scope

- Upgrade the potentiometer rig to real sensors (MPU6050 for vibration,

- Add authentication and multi-engine/multi-drone support.
- Expand fault scenario library and collect/incorporate real engine test-bench

- Add model confidence intervals / uncertainty quantification to the RUL
  estimator.
